# Profile keys

Every key `.keel/profile.json` may contain, what it does, and whether keel writes it.

Generated by `tests/generate-profile-keys.sh` from `templates/profile.schema.json`.
Do not edit by hand: `tests/validate-skills.sh` fails when this file and the schema
disagree, and names the command that regenerates it.

**Set by** is derived by running `keel init` against a throwaway fixture, so it cannot
drift from what init actually writes. A key marked **you** is one keel never writes: it
does nothing until a human adds it.

| Key | Type | Set by | Description |
|---|---|---|---|
| `keel_version` | string | `keel init` | Version of keel that last wrote this file. |
| `schema_version` | integer | `keel init` | Which set of profile fields this file has. Written by `keel init`, bumped only when a field is added, removed, renamed or moved. Absent means the file predates the field, which doctor treats as stale. |
| `project.name` | string | `keel init` | Name of this project, used in generated documents and reports. keel init takes it from the directory name; change it where the directory is not what the project is called. |
| `project.kind` | one of: `service`, `library`, `cli`, `frontend`, `plugin`, `docs` | `keel init` | `docs` means pre-implementation: no stack and no source files. doctor then skips the verify checks rather than failing on commands a documents-only repo cannot have. |
| `project.description` | string | `keel init` | One line saying what this project is for, in the terms its users would use. Skills quote it at the top of a snapshot or a PRD, so a reader who has never seen the repository knows what they are looking at. Left empty by init because only a human knows the answer. |
| `stack.language` | string | `keel init` | The primary language, which drives the verify commands and the conventions a skill applies. Read from a declared manifest such as package.json or go.mod for every language except plsql, which has no manifest format and is inferred from the shape of the tree instead: no other manifest present, .sql and .plsql dominant, and an Oracle-exclusive token in one of them. unknown means nothing was detected, and a skill asks rather than guessing. |
| `stack.runtime` | string | `keel init` | What actually executes the code: node, jvm, dotnet, python, native. Distinct from the language because several languages share a runtime and the runtime is what a deployment has to provide. |
| `stack.framework` | string | `keel init` | The application framework in use, such as nextjs, laravel or spring. none means the project uses its language's standard library and no framework, which is a real answer and not a gap. |
| `stack.package_manager` | string | `keel init` | How dependencies are installed and scripts are run, such as pnpm, poetry or cargo. Skills prefix commands with it, so a wrong value produces commands that do not run. A project with no package manager gets the string none rather than null. |
| `stack.also` | array | `keel init` | Every other language detected in this repository. The primary in `language` drives the verify commands; these get a language server each. |
| `stack.datastores` | array | `keel init` | Datastores this project talks to, detected from declared dependencies. Skills use it to know which failure modes are worth asking about: a service with postgres has migrations and transactions to reason about, one with none does not. |
| `stack.has_ui` | boolean | `keel init` | When true, the project has a user interface of some kind. It is read by three callers that each ask a different question of it, so each gates on it plus what it needs: the frontend standard applies when this is true and stack.framework is not flutter, because that reference is about the browser. See skills/coding-standards/references/frontend.md. |
| `verify.test` | string/null | `keel init` | The command that runs the whole test suite, exactly as a shell would run it. Read from what the project declares rather than inferred from the stack, because the real command is frequently not the idiomatic one. null means the project genuinely has none, and a skill asks instead of substituting a guess. |
| `verify.test_one` | string/null | `keel init` | Single test. `{path}` or `{name}` is substituted. Required by tdd and by the optional commit guard. |
| `verify.test_integration` | string/null | `keel init` | Tests against a running database. Kept separate so the fast suite stays fast; both run in CI. |
| `verify.lint` | string/null | `keel init` | Must be check-only. A command that rewrites files cannot gate. |
| `verify.format` | string/null | `keel init` | Must be check-only, like lint. `prettier --check .`, not `prettier --write .`. |
| `verify.format_fix` | string/null | `keel init` | The writing counterpart of format. Never run by a gate: it is what a refusal names as the remedy, so the person committing runs it and reads what it changed. |
| `verify.typecheck` | string/null | `keel init` | The command that checks types without producing a build. null for a language with no separate typecheck step, which is most of them. |
| `verify.build` | string/null | `keel init` | The command that produces the deployable artifact. null where there is nothing to build, such as an interpreted service run from source. |
| `verify.e2e` | string/null | `keel init` | The command that runs end-to-end tests against a running system. Separate from verify.test because it usually needs an environment, so a skill may run the unit suite and skip this one. |
| `verify.security` | string/null | `keel init` | The command that runs a security scanner, such as a dependency audit. null where the project has none; security-audit then does its own reading rather than reporting a clean scan that never ran. |
| `verify_notes` | object | **you** | Why a command is what it is, especially where it is deliberately not the stack's idiomatic one. Read by a human, and by anyone tempted to 'fix' it. |
| `artifacts.snapshot` | string/null | `keel init` | Path to an existing repository snapshot, where the project already has one under a different name. Skills read the mapped path instead of the default under docs_root, so a repository with its own naming convention is not duplicated. null means use the default. |
| `artifacts.prd` | string/null | `keel init` | Path to an existing requirements document, where the project already has one under a different name. null means use the default under docs_root. |
| `artifacts.stories` | string/null | `keel init` | Path to an existing backlog or stories document. null means use the default under docs_root. |
| `artifacts.architecture` | string/null | `keel init` | Path to an existing architecture document. null means use the default under docs_root. |
| `artifacts.decisions` | string/null | `keel init` | Path to an existing decision record directory, such as an adr/ folder the project already keeps. null means use the default under docs_root. |
| `artifacts.plans` | string/null | `keel init` | Path to an existing implementation plans directory. null means use the default under docs_root. |
| `gates.tdd` | one of: `required`, `warn`, `off` | `keel init` | Whether a failing test must be written before implementation code. Read by no skill, hook or CLI path today: the tdd skill asks for the cycle unconditionally, so changing this key changes nothing. Declared so the intent has somewhere to live once something enforces it. |
| `gates.coding_standards` | one of: `required`, `warn`, `off` | `keel init` | Whether a change must follow the conventions in the project's standards document. Read by no skill, hook or CLI path today, so nothing in keel enforces it; an agent that reads the profile may still act on it, observed 2026-08-20 in tests/evals/results.md. Declared for the same reason as gates.tdd. |
| `gates.review` | one of: `required`, `warn`, `off` | `keel init` | Whether review-code must run before a change ships. Read by no skill, hook or CLI path today: ship runs its own gate regardless, so changing this key changes nothing. |
| `gates.security_audit` | one of: `required`, `warn`, `off` | `keel init` | Whether security-audit must run before a change ships. required on anything touching money, credentials or personal data. warn elsewhere reports findings without blocking. |
| `gates.observability` | one of: `required`, `warn`, `off` | `keel init` | Whether new code must emit the logs and traces the observability standard describes. Read by no skill, hook or CLI path today, so changing it has no effect. A project with no telemetry backend does not need to set it to off; nothing is asking. |
| `gates.docs_updated` | one of: `required`, `warn`, `off` | `keel init` | Whether a change must land with the documents it makes wrong. Read by no skill, hook or CLI path today, so changing it has no effect. The obligation is carried by the standards document and by ship's own gate instead. |
| `gates.commit_guard` | one of: `required`, `warn`, `off` | `keel init` | The pre-commit hook `keel guard install` writes. off, the default, makes it inert, so installing the guard for its push protections does not impose a commit gate nobody asked for. required runs verify.format, verify.lint and verify.typecheck before each commit and refuses on a failure; warn reports and lets the commit through. |
| `gates.done_verified` | one of: `required`, `warn`, `off` | `keel init` | Drives hooks/done-guard on Stop and SubagentStop. required refuses to end a turn that edited code and never ran verify.test; warn says it and allows the stop. Off, or absent, and the hook does nothing. |
| `gates.context_watch` | boolean | **you** | false turns the session context watchdog off for this project. Declared here rather than left to additionalProperties because it is not a required/warn/off gate. |
| `gates.context_window` | integer | `keel init` | Context window in tokens for sessions in this project, written by keel init as 200000. It is a floor and not a ceiling: the watchdog raises it once a session is observed exceeding it, since the API would have refused the request otherwise, so a value that understates the window costs nothing beyond an early first estimate. It is never raised above 1000000, the largest window any current model offers, so a mistyped extra zero cannot silence the watchdog. A value at or below 200000 has no effect, because a floor only ever raises: KEEL_CONTEXT_WINDOW is how a smaller window is forced deliberately, and it is used as set except that it too is capped at 1000000. |
| `gates.context_warn_pct` | integer | **you** | Percentage of the window at which the watchdog starts warning. Default 70. |
| `gates.context_stop_pct` | integer | **you** | Percentage of the window at which the watchdog blocks tool calls until a handoff is written. Default 85. |
| `hard_block_paths` | array | **you** | Path patterns where a security finding cannot be overridden in conversation. Intended for auth, money movement, and personal data. Enforced by hooks/sensitive-guard, which asks a human before a commit touching one. Matched with fnmatch against repository-root-relative paths, where * crosses directory separators, and a bare directory such as 'src/auth' also matches everything under it. |
| `conventions.commit_style` | string | `keel init` | The commit message convention this repository follows. conventional means the type(scope): subject form, and skills write messages in it. Set it to none where the repository has no convention, rather than having keel impose one. |
| `conventions.default_branch` | string | `keel init` | The repository's default branch, which is frequently not the checked-out one. Skills refuse to implement here and repo-snapshot compares HEAD against it. |
| `conventions.working_branch` | string | **you** | The branch this project's work belongs on, where that is not a fresh branch per change. Read by no skill today, so setting it does not change what a skill proposes. Declared so a repository using one long-lived integration branch has somewhere to say so. |
| `conventions.protect_default_branch` | boolean | `keel init` | false lets the push guard allow a push straight to default_branch. Read by the pre-push hook from `keel guard install`, which otherwise refuses one, since work lands through a pull request. `git push --no-verify` is the one-off escape hatch. |
| `conventions.response_style` | one of: `terse`, `verbose` | `keel init` | terse keeps conversation replies short and leaves artifacts at full detail; the SessionStart hook injects the rule. verbose turns it off. Absent is treated as terse. |
| `conventions.explain_level` | one of: `technical`, `plain` | `keel init` | technical assumes the vocabulary of the thing being described; plain has chat replies define a technical term the first time they use it. It changes replies only: artifacts stay technical whatever this says, and the SessionStart hook picks its injected paragraph from this key and response_style together. Absent is treated as technical. |
| `observability.backend` | one of: `signoz`, `grafana`, `datadog`, `none` | `keel init` | Instrumentation is OpenTelemetry regardless, so the vendor sits behind the exporter and switching is configuration. |
| `observability.otlp_endpoint_var` | string | `keel init` | Name of the environment variable holding the OTLP endpoint, not the endpoint itself. The name is a fact about the project and belongs in a committed file; the value is a fact about an environment and does not. |
| `observability.log_shipping` | string | `keel init` | How logs reach the backend: otlp to export them directly, stdout to let the platform collect them, none where nothing is shipped. It decides whether generated code configures an exporter or simply writes to stdout. |
| `deploy.target` | string/null | `keel init` | Where this project runs once shipped, such as kubernetes, lambda or a plugin marketplace. setup-deployment reads it to know which pipeline shape applies. null means it has not been decided, which is different from having no deployment. |
| `deploy.ci` | string/null | `keel init` | The CI system that runs this project's pipeline, such as github-actions or gitlab-ci. null means there is none yet, and setup-deployment proposes one rather than assuming. |
| `deploy.registry` | string/null | **you** | Where built images or packages are published, as a registry host and path. Named here so a pipeline and a runbook agree on one value instead of each carrying its own copy. Credentials never belong here: this is the address, not the access. |
| `deploy.envs` | array | `keel init` | The environments this project deploys to, in promotion order, such as staging then production. An empty list means it deploys nowhere yet. Skills use the order to know what promotes to what. |
| `deploy.secrets_manager` | string/null | **you** | Where this project's secrets actually live, such as a named vault or a cloud secret store. Recorded so a runbook can say where to rotate a credential without a reader having to ask. It names the store, never a secret. |
| `plugins.recommended` | array | `keel init` | Plugins this project expects, as marketplace-qualified names such as typescript-lsp@claude-plugins-official. keel doctor names any that are not enabled, along with the command that installs them. A value here is preserved when init is re-run, so a curated list survives. |
| `plugins.excluded` | array | **you** | Plugins this project deliberately does not want, as marketplace-qualified names. Read by nothing today: plugin_report checks plugins.recommended only, so listing a plugin here does not stop it being recommended. Declared so a project has somewhere to record the decision once it is honoured. |
| `docs_root` | string | `keel init` | Must not be gitignored. keel init refuses when it is, because a skill would write there successfully and be invisible to every teammate. |
| `notes` | array | **you** | Project facts a skill should know that nothing else records. |
